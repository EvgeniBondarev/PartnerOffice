# PartnerOffice: архитектура и план

Кабинет для региональных партнёров: они работают с заказами Studio2 в рамках, которые задаёт владелец. Дизайн: [design/README.md](../design/README.md).

## Принципы

- Партнёр никогда не обращается к Studio2 напрямую. Все запросы идут через модуль `Areas/Partner` внутри Studio2Prod, который на каждом запросе применяет правила видимости.
- Заказы читаются live из БД Studio2 (без кэша и синхронизации).
- Действия над заказами вызывают существующие сервисы Studio2 и не дублируют их логику.
- Любой вход и любое действие пишутся в журнал.

## Размещение кода

| Репозиторий | Что лежит |
|---|---|
| Studio2Prod (`Areas/Partner`, `AppRepository/PartnerServices`, `OzonDomains/Models/Partner*`) | Бэкенд: API партнёра и владельца, правила, права, аудит, уведомления, миграции |
| PartnerOffice (этот репо) | React SPA на токенах `design/`; сборка копируется в `wwwroot/partner` Studio2Prod |

БД: MariaDB Studio2, новые таблицы с префиксом `Partner`. Миграции создаёт человек, автоматически миграции не меняются (правило Studio2Prod).

## Слои бэкенда

```
Browser (React SPA)
  │ cookie-сессия
  ▼
Areas/Partner
  ├─ Auth: логин+пароль (хеш) | Google OIDC по заранее добавленному email
  ├─ PartnerScopeEvaluator   правила партнёра → фильтр по заказам (по образцу AccessControl/DataScopeEvaluator)
  ├─ PartnerOrdersService    чтение заказов с применением scope
  ├─ PartnerActionsService   проверка галочки + scope → существующие сервисы Studio2
  ├─ PartnerAuditService     журнал
  └─ PartnerNotifier         Email / Telegram
        ▲
OzonWebhookService → хендлеры (NEW_POSTING, STATE_CHANGED, POSTING_CANCELLED) → IPartnerEventPublisher
```

## Модель данных

| Таблица | Назначение |
|---|---|
| `Partners` | логин, хеш пароля, Google email (необязательный), активен, каналы уведомлений |
| `PartnerRules` | правило видимости партнёра (имя, активно) |
| `PartnerRuleConditions` | условие правила: поле + множество значений |
| `PartnerPermissions` | галочки возможностей партнёра |
| `PartnerAuditLog` | входы и действия: кто, что, заказ, результат, время |
| `PartnerNotificationLog` | отправленные уведомления и ошибки доставки |

### Правила видимости

- Партнёру можно задать несколько правил; заказ виден, если подходит хотя бы под одно (объединение).
- Внутри правила: AND между полями, OR между значениями одного поля.
- Поля: статус, склад отгрузки, клиент, маркетплейс/кабинет, период дат, артикул/бренд.
- Заказ вышел из правил: пропадает у партнёра сразу.
- Заказ вне scope: 404, не 403, чтобы не раскрывать существование.
- Studio-части (`posting/1`, `posting/2`) идут как отдельные заказы, действия над ними нормализуются к родительскому posting Ozon (`OzonPostingNumberHelper`).

### Права (галочки на партнёра)

| Флаг | Действие |
|---|---|
| `LabelPrint` | печать и скачивание этикетки |
| `Assemble` | сборка / отгрузка |
| `TrackNumber` | ввод трек-номера |

Просмотр заказов доступен всегда.

## Действия

| Действие | Реализация |
|---|---|
| Печать этикетки | `OzonLabelPrintService`: страна изготовителя → экземпляры (`OzonExemplarService`: ЧЗ/ГТД/РНПТ) → при `ship_not_available` показать причины и остановиться → ship → label v3 → PDF как есть |
| Сборка / отгрузка | Смена статуса по цепочке Studio2 + ship в Ozon (`OrdersOzonShipService`); учесть `SetClient` для не-дефолтного кабинета Ozon |
| Трек-номер | Валидация формата по перевозчику (набор перевозчиков и форматов настраивается), запись в заказ Studio2 |

Только `ClientType = OZON`; заказы Yandex Market пропускаются с понятным сообщением.

## Уведомления

| Кому | О чём |
|---|---|
| Партнёру | новый заказ попал под его правила |
| Владельцу | партнёр выполнил действие (сборка, отгрузка, трек, печать) |

Каналы: email и Telegram, владелец выбирает на каждого партнёра. Источник событий: in-process хуки в обработчиках Ozon webhook (`POST /Studio2/OzonWebhook/Receive`), доставка через Hangfire с повторами. Новый HTTP-webhook не нужен.

## Вход

- Логин и пароль задаёт владелец. Пароль хранится только в виде хеша.
- Если у партнёра указан Google email, доступен вход через Google; другие Google-аккаунты не пускаются.
- Блокировка партнёра обрывает его сессии.

## Кабинеты

**Владелец:** партнёры (создание, логин/пароль, Google email, блокировка) → правила с предпросмотром числа попадающих заказов → галочки → каналы уведомлений → журнал действий.

**Партнёр:** список заказов (номер, название, этикетка-превью, картинка, артикул, статус, склад, клиент, дата) с фильтрами → карточка заказа → действия по галочкам.

## Допущения и открытые вопросы

| Вопрос | Пока принято |
|---|---|
| Трек-номер: хранить только в Studio2 или слать в Ozon, список перевозчиков | Только Studio2; перевозчики и форматы настраиваемые, начальный список уточнить |
| Владельцев несколько? | Один владелец, ролей нет |
| Масштаб | до 10 партнёров, до 1 тыс. заказов в день |
| Деплой | Docker на сервере Studio2 |

## Этапы

1. Бэкенд, основа: таблицы, аутентификация партнёра и владельца, CRUD партнёров, правила, права, аудит.
2. Бэкенд, заказы: `PartnerScopeEvaluator`, список и карточка заказа, этикетка-превью и картинка.
3. Бэкенд, действия: печать этикетки, сборка/отгрузка, трек-номер.
4. Бэкенд, уведомления: хуки в webhook, Email, Telegram, журнал.
5. Фронт: каркас SPA, вход, кабинет владельца, кабинет партнёра.
6. Docker, раздача SPA из Studio2, smoke-тесты, документация в `docs/` Studio2Prod.
